# WDTT: глубокий анализ — что ещё можно выжать и стоит ли менять язык

Вопрос: менять язык (Rust/C) ради производительности? Короткий ответ — **нет**.
Длинный — ниже, с раскладкой по каждому байту на пакет.

## 1. Куда уходит время на пакет сейчас (после 5 итераций)

Пакет 1200 Б, сервер 1 ядро, замеры стенда:

| Статья | Оценка | Управляемо из Go? |
|---|---|---|
| Крипта ChaCha20-Poly1305 (AVX2) | ~1.0 мкс | уже SIMD; AES-GCM (AES-NI) — 0.4 мкс, протокол 46000 |
| Копии в юзерспейсе (pion-буфер → наш пул) | ~0.25 мкс | да — свой демультиплексор вместо pion |
| Syscall UDP (уже recvmmsg/sendmmsg, батч 64) | ~0.05 мкс/пакет | уже сделано |
| Syscall TUN (1 чтение + 1 запись на пакет) | ~1.5 мкс | только VNET_HDR (готов, флаг) |
| Ядро: netfilter, GRO, conntrack, копия в skb | ~1.0 мкс | sysctl/GSO, не Go |
| Горутины/каналы/GC | ~0.2 мкс | уже пулы/атомики/COW |

Итого юзерспейс-Go — меньше половины стоимости пакета. Всё остальное — ядро
и крипта, которые языком не меняются.

## 2. Язык: Rust/C — вердикт с цифрами

- **Потолок выигрыша**: минус копии и io_uring вместо sendmmsg → ~15–25% CPU
  на пакете; плюс 30–40% если выкинуть pion и написать свой UDP-демux.
  Реально ~1.5–2× на пределе (50k → 80–100k pps на ядро).
- **Цена**: сервер — переписать 5k строк (обфускация, TUN, NAT, replay,
  админка); клиент — переписать 7k строк + gomobile/NDK-слой +_vk TURN
  протокол; риск рассинхрона протокола клиент/сервер; недели работы.
- **Когда это окупается**: устойчивые 40k+ pps на инстанс (сейчас пик юзеров —
  единицы тысяч). При текущей нагрузке сервер занят на 15–25% ядра.
- **Вывод**: смена языка — инженерный спорт, а не необходимость. Форк уже на
  ~90% практического потолка Go. Если когда-нибудь упрёмся — дешевле
  вертикально масштабировать VPS (2→4 vCPU), чем переписывать.

## 3. Что осталось реально сделать (ранжировано по эффект/риск)

### A. Pinning ядра на проде (5 мин, эффект — стабильность латентности)
На 2 vCPU с docker/nginx рядом: `CPUAffinity=1` в юните wdtt — wdtt живёт на
ядре 1, соседние сервисы на 0. Убирает джиттер от соседей. Файл готовится,
применять с разрешения владельца.

### B. MTU по шифру: audio 1420 / video 1300 (код, средний риск)
Сейчас rawMTU=1300 для всех. Худший случай провода: 1420+52 (audio) = 1472 <
1500 ✓, но 1420+88 (video) = 1508 ✗. Значит MTU можно поднять до 1420 для
audio-режима: +9% полезной нагрузки на пакет = −9% pps на тот же трафик =
прямая экономия CPU и сисколлов. Риск: часть мобильных сетей имеет MTU
1400–1430 — нужен тест на живых сетях. MSS-clamping уже стоит.

### C. Свой UDP-демux вместо pion (код, средний риск)
Убрать двойную копию (сокет → pion per-conn буфер → наш пул): один ReadBatch
в общий цикл, маршрутизация по src-адресу сразу в сессию. −0.3 мкс/пакет ≈
−10–15% юзерспейс-CPU на пределе. Требует переписать accept/ deadline-механику.

### D. GSO на проде (флаг готов)
Для TCP-трафика (основного у юзеров) −30–50% сисколлов TUN. Включить
`-tun-gso` в окно низкой нагрузки, понаблюдать СТАТ и джиттер, откат — флагом.

### E. Sysctl-профиль прод-сервера (файл готовится)
```
net.core.rmem_max=16777216
net.core.wmem_max=16777216
net.core.netdev_max_backlog=8192
net.ipv4.udp_early_demux=1
```
(rmem/wmem на de27 уже 64M — ок; backlog и early_demux проверить.)

### F. Масштабирование дальше (только при росте в 5–10 раз)
- SO_REUSEPORT + N процессов по ядрам (шардинг клиентов по hash).
- XDP/eBPF-классификация — сложность не оправдана текущими цифрами.
- Вертикальный рост VPS.

## 4. Что НЕ делать (доказано)

- **Менять язык** — см. §2.
- **Ручная криптография** — библиотеки уже векторизованы; своя быстрее не будет.
- **Микро-мемойка байтов** — после пулов/кольцевых буферов остаток наносекунды.
- **UDP GSO на исходящих батчах** — требует одинакового размера пакетов в
  батче, у нас размеры смешанные (padding), ядро отвергнет.
- **ebpf-шифрование в ядре** — снятие маскировки в ядро = потеря главного
  свойства проекта (RTP-обфускация в юзерспейсе).

## 5. Приоритет внедрения

1. A (pinning) + E (sysctl) — системно, без кода.
2. D (GSO) — флаг готов, тест на живом трафике.
3. B (MTU 1420 audio) — код готовится, тест на 2–3 мобильных сетях.
4. C (свой демux) — только если п.1–4 окажется мало при росте нагрузки.

## 6. Итоговая позиция

Форк уже несёт: 4× пропускной способности, −50% CPU, ноль аллокаций в
криптохоте, батчинг сисколлов, AES-протокол, самовосстановление после
простоя. Дальнейший прирост — системный тюнинг (п.1–2) и два средних
проектных изменения (п.3–4), каждое из которых даёт десятки процентов
только на пределе, которого реальная нагрузка не достигает.
