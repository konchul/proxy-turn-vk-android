# qWDTT: оптимизации и изменения 

Полный список изменений относительно апстрима proxy-turn-vk-android. Всё измерено
на тестовом стенде (VPS 1 vCPU, пакет 1200 Б, полный цикл через TUN) и обкатано
на живом проде.

## 1. Сервер — горячий путь raw-режима (`server/raw.go`, `statistics.go`)

- Карта сессий `map[uint32]` — IPv4 берётся прямо из байтов пакета: ноль
  аллокаций на lookup (было `net.IP().String()` — аллокация на каждый пакет).
- Карта читается под `RWMutex.RLock`, ротация чанков — в единственном писателе
  (`downlinkLoop`): даунлинк всех клиентов больше не сериализуется одним локом.
- `bytes.HasPrefix` вместо `string(пакет)` — минус аллокация размером с пакет
  на каждый аплинк.
- `SetReadDeadline` перевзводится раз в 5 с вместо каждого пакета (минус
  setsockopt на пакет).
- Счётчики трафика — атомики в сессии, флеш в БД раз в 10 с (было: глобальный
  мьютекс + map-поиск на каждый пакет в обе стороны). Остатки закрывшихся
  сессий сохраняются — трафик не теряется.

## 2. Сервер — крипто-слой (`server/obfs.go`)

- `crypto/rand` → xorshift `fastPRNG` для padding: минус 2 getrandom-сисколла
  на каждый исходящий пакет (padding — несекретный шум).
- Nonce заполняется на стеке (`obfsFillNonce`): минус аллокация 12 Б на пакет
  в обе стороны.
- Кэш AEAD на массиве `[32]byte` вместо `string(key)`: минус аллокация на
  каждый пакет.
- Anti-replay: кольцо на 8192 слотов O(1), ноль аллокаций — вместо
  `map[nonce]ts` с полным проходом-чисткой раз в 8192 пакета.

## 3. Сервер — батчинг системных вызовов

`listenWrapped(..., batch=true)` включает pion `BatchIOConfig`:
`recvmmsg` на приёме и `sendmmsg` на отправке (через `golang.org/x/net/ipv4`)
на raw-листенерах. Батч 64 пакета, флаш 200 мкс — цена ≤1 мс RTT в простое.

## 4. Сервер — протокол AES-256-GCM, порт 46000

- Тип `obfsCipher`; фрейминг, ключи и nonce-схема идентичны ChaCha-версии,
  отличается только AEAD. AES-NI даёт −3–6% CPU и меньше потерь.
- Флаг `-listen-raw-aes 0.0.0.0:46000`: отдельный порт для нового протокола.
  Старые клиенты на него не зайдут (рукопожатие не пройдёт), порты
  56000/56002/56003 работают по-старому — полная обратная совместимость.
- Клиент выбирает шифр автоматически по порту пира (46000 = AES).

## 5. Сервер — VNET_HDR (GSO/GRO), флаг `-tun-gso`

- TUN с `IFF_VNET_HDR` + `TUNSETOFFLOAD` (TSO4/TSO6/ECN, авто-фолбэк).
- Даунлинк: GSO-суперкадры (до 64 КБ за один Read) сегментируются в
  юзерспейсе на пакеты ≤ MTU: корректные TCP seq, PSH на последнем сегменте,
  пересчёт IPv4/TCP/UDP чексумм (кадр приходит с CHECKSUM_PARTIAL).
  Поддержка TCPv4/TCPv6/UDP_L4. Юнит-тесты — PASS.
- Аплинк: 10-байтовый virtio-префикс без лишней копии → ядро может
  GRO-склеивать TCP клиента.
- На ядре 5.15 UDP_L4 через TUN не проходит (проверено ethtool) — выигрыш
  только на TCP; поэтому флаг выключен по умолчанию.

## 6. Фикс «после простоя туннель не восстанавливается»

- Сервер отвечает понгом (1 байт) на keepalive клиента — обе ветки (raw и
  DTLS/WG). Клиентские ридеры понг съедают, в TUN он не попадает.
- Клиент: таймаут чтения сессии 30 мин → 90 с; 3 таймаута подряд без
  даунлинка → сессия принудительно пересоздаётся (новый TURN-allocation =
  новый UDP 4-tuple, обходит молчаливый дроп провайдера). Раньше мёртвая
  сессия не завершалась никогда.

## 7. Клиент (`go_client/`)

- `obfs.go`: fastPRNG, стек-nonce, AEAD-кэш, replay-кольцо, pooled-выходной
  буфер (`obfsWrapPacketBuf`) — ноль аллокаций в криптохоте.
- `session.go`: keepalive 10 с → 25 с (пробуждения радио −60%, TURN
  permission 300 с и NAT ≥30 с — с запасом), восстановление из п.6.
- `dispatcher.go`: глобальный мьютекс → copy-on-write снапшот воркеров,
  горячий путь без лока.

## 8. Приложение и деплой

- Встроенный в APK сервер собирается стрипнутым (`-ldflags="-s -w"`): −4.5 МБ.
- Деплой поддерживает AES-порт (`WDTT_AES_PORT` в deploy.sh): добавляет
  `-listen-raw-aes` и правило файрвола. Задеплоенные порты запоминаются.
- В настройках Raw-режима — выбор шифра (ChaCha20 · 56003 / AES-256 · 46000),
  порт меняется автоматически.
- APK 86.5 → 18.4 МБ (реальный R8-релиз; отдельные шрифты/иконки не трогали).

## 9.1 Flood-бенчмарк (односторонний, MTU 1350, потолок сервера)

Сервер обрабатывает **>110 000 pps ≈ 1.2 Гбит/с на одно ядро при 0% потерь**
(AES-256-GCM). Во всех точках 0% потерь — потолок достигал генератор нагрузки,
не сервер.

| Цель pps | CPU (AES) | Пропускная способность (AES) | CPU (ChaCha) | Пропускная способность (ChaCha) |
|---|---|---|---|---|
| 50 000 | 41.5% | 368 Мбит/с | 46.2% | 319 Мбит/с |
| 100 000 | 61.7% | 779 Мбит/с | 69.3% | 601 Мбит/с |
| 200 000 | 68.5% | 1068 Мбит/с | 73.8% | 947 Мбит/с |
| 300 000 | 78.5% | **1194 Мбит/с** | 77.0% | 1027 Мбит/с |
| 500 000 | 75.3% | 1072 Мбит/с | 79.5% | 1244 Мбит/с |

AES-256-GCM стабильно быстрее ChaCha20 на том же бинарнике.

**Выводы.** При равной нагрузке оптимизированный сервер ест на 15–19% CPU
меньше базы (100k pps: 71.7% → 58.2%) и держит больший потолок (300k цели:
база захлёбывается на 92k pps, форк выдаёт 114–117k pps = 1.23–1.26 Гбит/с).
AES-протокол быстрее ChaCha при том же коде. GSO добавляет ещё −3–5% CPU —
скромно для UDP-нагрузки (ядро 5.15 не оффлоадит UDP_L4 через TUN); на
TCP-трафике выигрыш ожидаемо больше.

## Совместимость

Клиенты апстрима работают с новым сервером без изменений (все старые порты —
ChaCha). Новые возможности (AES, raw) — через соответствующие порты/режимы.
